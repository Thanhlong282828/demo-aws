# D32 — Automated Testing

## Học gì?

Feature tests qua Laravel kernel + MySQL, regression và transaction rollback; ưu tiên business risk.

## Tự làm theo source

Đọc bảng từ trên xuống. Bấm vào tên file để mở source, tìm hàm/đoạn code được mô tả ở cột bên phải.

| File cần mở | Code cần đọc và nhiệm vụ của code |
| --- | --- |
| [tests/Feature/Week5ApiTest.php](../tests/Feature/Week5ApiTest.php) | Đọc test product, auth/token, owner, category, eager load và lỗi production. |
| [tests/Feature/Week4BusinessTest.php](../tests/Feature/Week4BusinessTest.php) | Checkout order/items/stock/cart/coupon, double checkout và terminal status. |
| [phpunit.xml](../phpunit.xml) | Database minishop_week5_test riêng; RefreshDatabase có thể xóa/reset dữ liệu test. |

Đọc lần lượt, tự gõ lại phần thay đổi trên branch luyện tập; gửi request hoặc chạy test sau từng bước. Controller không tin role/user_id/total từ client. Đối chiếu response với [API docs](api.md).

## Terminal cần chạy

Bắt đầu tại thư mục project:

```bash
cd "$HOME/Desktop/xinviec/weekfiifileone"
php artisan test --compact
php artisan test --compact --filter=midcheckout_failure
php artisan test --compact --filter=test_guest_product_list_is_json_and_paginated
```

82 tests /338 assertions PASS. Regression thực tế: bỏ route index Products → test list FAIL 405; khôi phục route → PASS. Rollback test ném exception lúc tạo order item thứ2, assert không có order/items dở, stock/cart/coupon giữ nguyên. Chỉ phá code trên local, không trên VPS.

## Câu hỏi kiến thức và đáp án tham khảo

Cách học: tự trả lời trước, sau đó đối chiếu đáp án và source. Đáp án để ôn tập, không chứng nhận bạn đã tự làm hoặc đã đạt điểm.

| Câu hỏi | Đáp án / kiến thức cần hiểu | Code hoặc lệnh nào? (bấm để mở) | Code / lệnh đó làm gì? |
| --- | --- | --- | --- |
| 1. Automated test giải quyết vấn đề gì? | Lặp lại kiểm tra bằng code để phát hiện hành vi sai và regression khi sửa project. Suite kiểm response, quyền và dữ liệu sau nghiệp vụ thay vì chỉ nhìn trang có mở được hay không. | [`test_admin_product_crud_persists()`](../tests/Feature/Week5ApiTest.php) | Kiểm tra CRUD và dữ liệu lưu DB tự động. |
| 2. Manual test có còn cần không? | Có. Cần kiểm giao diện, thao tác người dùng và môi trường thật; automated tests chỉ chứng minh những tình huống đã viết. Smoke HTTPS bổ sung bằng chứng Nginx/PHP-FPM/TLS mà feature test local không kiểm hết. | [`Smoke test HTTP/HTTPS`](../docs/D34.md) | Kiểm tra môi trường triển khai thật ngoài test tự động. |
| 3. Feature test là gì ở mức em hiểu? | Là test hành vi một tính năng qua nhiều thành phần, thường gửi request vào Laravel kernel rồi assert status/JSON/database. Nó rộng hơn test một hàm đơn lẻ và không nhất thiết mở trình duyệt thật. | [`test_guest_product_list_is_json_and_paginated()`](../tests/Feature/Week5ApiTest.php) | Gửi request qua ứng dụng và kiểm tra JSON/phân trang. |
| 4. Regression là gì? | Là chức năng trước đây hoạt động bị hỏng sau thay đổi. Experiment của project bỏ GET Product index làm test FAIL405; khôi phục route thì test PASS. | [`test_logout_revokes_token()`](../tests/Feature/Week5ApiTest.php) | Phát hiện thay đổi làm token đã logout dùng lại được. |
| 5. Chỉ test happy path đã đủ chưa? | Chưa. Cần cả dữ liệu sai, user thiếu quyền, tài nguyên không có và lỗi giữa transaction; nếu chỉ test Admin tạo Product hợp lệ thì có thể bỏ sót Guest/User ghi trái phép. | [`test_invalid_product_has_consistent_errors()`](../tests/Feature/Week5ApiTest.php) | Kiểm tra input sai, không chỉ luồng thành công. |
| 6. Authorization có đáng test không? | Có vì sai quyền có thể làm lộ đơn hàng hoặc cho phép sửa dữ liệu trái phép. Test USER→Admin API, Guest→protected API và User A→Order B có giá trị cao. | [`test_other_users_order_is_forbidden()`](../tests/Feature/Week5ApiTest.php) | Xác nhận user không xem được đơn người khác. |
| 7. Validation có đáng test không? | Có vì input sai có thể phá quy tắc DB/nghiệp vụ. Ví dụ test price âm, stock âm và category không tồn tại nhận422, đồng thời không tạo Product sai. | [`test_invalid_product_has_consistent_errors()`](../tests/Feature/Week5ApiTest.php) | Kiểm tra lỗi validation có status và cấu trúc đúng. |
| 8. Checkout transaction có đáng test không? | Rất đáng vì liên quan order/items/stock/cart/coupon cùng lúc. Test ném lỗi ở item thứ2 để xác nhận tất cả thay đổi trước đó rollback, không trừ tồn hoặc tạo đơn nửa chừng. | [`test_midcheckout_failure_rolls_everything_back()`](../tests/Feature/Week4BusinessTest.php) | Kiểm tra checkout lỗi giữa chừng rollback dữ liệu. |
| 9. Test fail có nghĩa implementation chắc chắn sai không? | Không. Có thể implementation sai, expectation sai, fixture sai hoặc môi trường/DB bị lỗi. Đọc assertion và log, đối chiếu requirement; không sửa code chỉ để chiều một test có kỳ vọng sai. | [`DB_DATABASE=minishop_week5_test`](../phpunit.xml) | Đối chiếu môi trường DB test trước khi kết luận lỗi code. |
| 10. 100% coverage có đồng nghĩa app không bug không? | Không. Coverage đo code được chạy qua, không chứng minh dữ liệu/assertion đủ hoặc mọi business rule đúng. Project ưu tiên flow có rủi ro, không tuyên bố100% coverage. | [`test_expired_token_is_rejected()`](../tests/Feature/Week5ApiTest.php) | Đây là một kịch bản cụ thể; test không chứng minh mọi tình huống đều đúng. |
