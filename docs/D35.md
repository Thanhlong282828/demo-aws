## Câu hỏi kiến thức và đáp án tham khảo

Cách học: tự trả lời trước, sau đó đối chiếu đáp án và source. Đáp án để ôn tập, không chứng nhận bạn đã tự làm hoặc đã đạt điểm.

Đây là30 câu Project Defense trong đề, chia6 nhóm. Phần Live Change45 phút vẫn tự làm không AI; không cung cấp sẵn code dashboard ở đây.

### Nhóm 1 — Project

**Câu 1. Project giải quyết vấn đề gì?**

**Đáp án:** Mini Shop cho phép khách xem catalog, user mua hàng qua giỏ/checkout và admin quản lý catalog/đơn. Mục tiêu portfolio là chứng minh flow backend có quyền, validation và transaction, không phải hệ thống thương mại quy mô lớn.

**Câu 2. Project có những loại user nào?**

**Đáp án:** Guest được xem sản phẩm/danh mục và đăng ký/đăng nhập; USER có giỏ và đơn riêng; ADMIN có thêm quyền quản lý Product/Category và mọi đơn qua endpoint admin. Role mới mặc định USER, không nhận ADMIN từ form đăng ký.

**Câu 3. Main business flow là gì?**

**Đáp án:** Đăng ký/đăng nhập → xem Product → thêm/sửa giỏ → checkout → tạo Order/OrderItems và giảm stock → xem đơn; Admin xác nhận, hoàn tất hoặc hủy theo luật. Tất cả bước ghi cần kiểm input và quyền ở server.

**Câu 4. Tech stack của project là gì?**

**Đáp án:** Laravel13, PHP theo lock cần8.4.1+, nwidart/laravel-modules13, Sanctum4, MySQL8, Blade và PHPUnit12. Production chạy PHP8.5 trên Ubuntu26.04 EC2, Nginx/PHP-FPM và HTTPS tự gia hạn.

**Câu 5. Vì sao chọn Laravel?**

**Đáp án:** Câu trả lời tham khảo: Laravel có routing, Eloquent, validation, auth, migration và testing giúp triển khai flow nhất quán. Modules tách Product/Category/Shop; người học phải tự giải thích sự lựa chọn, không nói đã tự thiết kế mọi thứ nếu có AI hỗ trợ.

### Nhóm 2 — Database

**Câu 6. Main tables là gì?**

**Đáp án:** users, categories, products, cart_items, coupons, orders, order_items và personal_access_tokens; còn có bảng hạ tầng như migrations/cache/jobs. Đọc migration để phân biệt dữ liệu nghiệp vụ với bảng framework.

**Câu 7. Order và OrderItem khác nhau thế nào?**

**Đáp án:** Order giữ thông tin chung như user, status và tổng tiền; OrderItem giữ từng dòng sản phẩm, quantity và snapshot giá/tên. Một Order có nhiều OrderItems, giúp lưu nhiều sản phẩm mà không lặp thông tin chung.

**Câu 8. Vì sao lưu unit_price trong OrderItem?**

**Đáp án:** Để giữ đơn giá tại thời điểm mua; nếu Product đổi giá, đơn cũ vẫn đúng lịch sử. Project lưu unit_price integer theo1/100 VND; không lấy giá Product hiện tại để tính lại đơn cũ.

**Câu 9. Transaction dùng ở đâu?**

**Đáp án:** CheckoutService dùng DB::transaction cho order/items/stock/coupon/cart; transition status cũng dùng transaction khi cập nhật trạng thái và hoàn stock. Row locks bảo vệ dữ liệu đang tranh chấp, không chỉ dựa vào kiểm stock ở giao diện.

**Câu 10. Nếu checkout fail giữa chừng thì sao?**

**Đáp án:** Exception trong transaction khiến thay đổi chưa commit rollback: không có Order/Items dở, stock/cart/coupon không bị update một phần. Test midcheckout_failure cố tình lỗi ở item thứ2 để xác minh điều đó.

### Nhóm 3 — Laravel

**Câu 11. Route, Controller và Model có vai trò gì?**

**Đáp án:** Route ánh xạ method/URL tới hành động và gắn middleware; controller nhận request, phối hợp validation/service rồi trả response; model biểu diễn dữ liệu và quan hệ qua Eloquent. View là Blade ở web, còn API Resource định dạng JSON.

**Câu 12. Validation được làm thế nào?**

**Đáp án:** Product/Category dùng FormRequest; auth/cart/status có request->validate; service kiểm thêm quy tắc nghiệp vụ có thể đổi trong lúc xử lý như tồn kho và status transition. Chỉ lấy validated data, không mass assign toàn bộ request.

**Câu 13. Authentication được làm thế nào?**

**Đáp án:** Web dùng session sau login và CSRF cho form; API dùng Sanctum bearer token, Hash::check cho mật khẩu, token8 giờ và logout revoke. Mật khẩu được hash, token DB cũng lưu hash, không lưu raw token để đọc lại.

**Câu 14. Authorization được làm thế nào?**

**Đáp án:** Middleware Admin kiểm role trước route quản trị; Order controller lọc user_id hoặc so owner với request user. Dù user tự gửi direct request cũng bị chặn; Blade chỉ ẩn/hiện menu, không thay security backend.

**Câu 15. Eloquent relationship là gì?**

**Đáp án:** Là cách khai báo quan hệ để query đối tượng liên quan: Product belongsTo Category, Category hasMany Products, Order hasMany Items. Dùng eager loading khi list cần relationship để tránh query từng dòng.

### Nhóm 4 — API

**Câu 16. API khác web routes thế nào?**

**Đáp án:** Web routes phục vụ HTML/redirect và dùng session/CSRF cho flow trình duyệt; API routes trả JSON/status cho client và các endpoint bảo vệ dùng Sanctum. Cùng model/service có thể dùng chung, không viết lại business rule ở hai nơi.

**Câu 17. 401 và403 khác nhau thế nào?**

**Đáp án:** 401 là chưa xác thực được;403 là đã xác thực nhưng thiếu quyền. Ví dụ Guest POST Product→401, USER có token POST Product→403, Admin input sai→422.

**Câu 18. REST endpoints được thiết kế thế nào?**

**Đáp án:** Dùng tài nguyên Product/Category/Order, noun URL và method GET/POST/PUT/PATCH/DELETE. Read public hoặc theo owner; write catalog chỉ Admin; admin order management tách /api/admin/orders. Thiết kế theo use case, không expose mọi table.

**Câu 19. API được bảo vệ thế nào?**

**Đáp án:** auth:sanctum xác thực, Admin middleware và ownership kiểm quyền, validation bảo vệ input, pagination hạn chế response lớn, login có throttle và HTTPS bảo vệ đường truyền. Những lớp này bổ sung cho nhau, không thay thế nhau.

**Câu 20. Dùng Postman của project thế nào?**

**Đáp án:** Import collection và local/production environment, chọn base_url, chạy Login để lưu token rồi gọi request đúng quyền. ID được lưu sau create; order_id phải thuộc user; export token để rỗng và thử write local trước.

### Nhóm 5 — Testing

**Câu 21. Project test những gì?**

**Đáp án:** 82 tests với338 assertions đã PASS trên MySQL: CRUD, auth/token, role/owner, validation, cart/checkout, snapshot, stock/coupon, rollback, double checkout, terminal status, pagination/eager loading và production error response. Ngoài ra có35 HTTP checks HTTPS đã PASS.

**Câu 22. Tại sao cần test checkout?**

**Đáp án:** Vì lỗi có thể khiến dữ liệu tài chính/tồn kho không nhất quán, mất giỏ hoặc tạo trùng đơn. Cần kiểm happy path, thiếu stock, lỗi giữa transaction và request retry, không chỉ assert redirect200.

**Câu 23. Feature test là gì?**

**Đáp án:** Test một hành vi đi qua Laravel kernel và các lớp liên quan, assert HTTP/JSON và DB. Nó không tự xác nhận DNS/TLS/Nginx ở production, nên cần smoke test thật.

**Câu 24. Regression là gì trong project này?**

**Đáp án:** Là sửa code làm hỏng flow cũ; experiment bỏ route GET index khiến test list nhận405 thay200. Restore route làm test PASS, cho thấy test bắt được đúng regression đó, không chứng minh bắt mọi bug.

**Câu 25. Khi test fail thì làm gì?**

**Đáp án:** Đọc tên test, expected/actual và trace; kiểm requirement, fixture, env/DB rồi tìm root cause. Sửa đúng nguyên nhân và chạy lại test liên quan; không skip test chỉ vì demo vẫn mở được.

### Nhóm 6 — Production

**Câu 26. Project deploy ở đâu?**

**Đáp án:** AWS EC2 ap-southeast-2, instance minishop-week5 loại t3.micro, Ubuntu26.04,20GiB gp3. Demo tại https://54.252.208.88/products, MySQL cùng VPS; IP này có thể thay đổi sau stop/start.

**Câu 27. Environment production được cấu hình ra sao?**

**Đáp án:** APP_ENV=production, APP_DEBUG=false, APP_URL HTTPS, SESSION_SECURE_COOKIE=true, DB credentials production riêng và config cache được tạo lại khi đổi cấu hình. Nginx chỉ phục vụ public/, PHP chạy qua PHP-FPM.

**Câu 28. Secrets được quản lý thế nào?**

**Đáp án:** Không commit .env/SSH key/token; .env.example chỉ placeholder. APP_KEY và DB password production được sinh trên VPS, file .env quyền640 với owner/group phù hợp; audit pattern giúp phát hiện một số loại secret, không phải bảo đảm tuyệt đối.

**Câu 29. Log của project nằm ở đâu?**

**Đáp án:** Laravel log trong storage/logs/laravel.log, Nginx error log trong /var/log/nginx/error.log; PHP-FPM và certbot xem bằng journalctl theo service. Log cần đủ dữ kiện để debug nhưng không chứa password/token thô.

**Câu 30. Production lỗi thì debug thế nào?**

**Đáp án:** Theo lớp URL/TLS → Nginx → PHP-FPM → Laravel/log → env/cache → MySQL → file permissions; dùng status, thời điểm và log để chọn lớp kế tiếp. Với bản deploy này từng gặp SSH source IP khác, metadata macOS và thiếu cache path; runbook D34 ghi cách xử lý.
