## Câu hỏi kiến thức và đáp án tham khảo

Cách học: tự trả lời trước, sau đó đối chiếu đáp án và source. Đáp án để ôn tập, không chứng nhận bạn đã tự làm hoặc đã đạt điểm.

| Câu hỏi | Đáp án / kiến thức cần hiểu | Code hoặc lệnh nào? (bấm để mở) | Code / lệnh đó làm gì? |
| --- | --- | --- | --- |
| 1. API documentation phục vụ ai? | Cho developer/client tích hợp API, QA kiểm thử và người review project. Họ cần biết URL, method, headers, input, permission, response và status mà không phải đoán từ code. | [`HTTP method / URL / body / response`](../docs/api.md) | Mô tả contract cho người gọi API. |
| 2. Postman dùng để làm gì? | Dùng để gửi HTTP request, xem response và lưu các request/test scripts phục vụ kiểm tra API. Trong project, login script lưu token để thử request bảo vệ. | [`request`](../docs/postman/Mini-Shop-API.postman_collection.json) | Lưu request mẫu để gửi và kiểm tra response. |
| 3. Collection là gì? | Là nhóm request có thể lưu, chia folder và chia sẻ cùng cấu hình/test scripts. Mini Shop Collection có Authentication, Products, Categories và Orders, tổng17 requests. | [`item`](../docs/postman/Mini-Shop-API.postman_collection.json) | Gom request theo nhóm trong một collection. |
| 4. Environment variable giúp gì? | Cho phép đổi base_url, token hoặc id mà không sửa từng request. Chọn local hoặc production environment; base_url trong collection không có /api vì path request đã thêm /api. | [`base_url / token`](../docs/postman/local.postman_environment.json) | Đổi môi trường mà không sửa từng request. |
| 5. Vì sao không hard-code production token? | Token hard-code dễ bị lộ khi chia sẻ/commit và nhanh hết hiệu lực. Export environment để token rỗng, login lại lấy token mới; đừng nhầm mật khẩu demo công khai với token hoạt động. | [`{{token}}`](../docs/postman/Mini-Shop-API.postman_collection.json) | Tham chiếu token môi trường thay vì chép token thật vào request. |
| 6. Consistent JSON response quan trọng thế nào? | Client có thể đọc data, message, errors theo quy ước chung thay vì viết logic riêng cho từng endpoint. List trong project thêm links/meta, detail có data object, validation có message/errors. | [`toArray()`](../app/Http/Resources/ProductResource.php) | Giữ các trường sản phẩm nhất quán giữa các response. |
| 7. Endpoint naming nên dùng noun hay action tùy tiện? | Ưu tiên danh từ tài nguyên và HTTP method, như /products với GET/POST; tránh /getAllProducts, /deleteProduct tùy tiện. Một số thao tác đặc biệt như /login hoặc /logout được đặt tên theo use case rõ ràng. | [`Route::apiResource('products', ProductController::class)`](../Modules/Product/routes/api.php) | Dùng danh từ products và HTTP method cho CRUD. |
| 8. API versioning là gì ở mức concept? | Là quản lý các phiên bản contract để thay đổi không tương thích không làm hỏng client cũ, ví dụ /api/v1 và /api/v2. Project hiện giữ /api/... theo đề, chưa triển khai version prefix. | [`Route::apiResource('products', ProductController::class)`](../Modules/Product/routes/api.php) | Hiện dùng /api/products; /api/v1 là ý tưởng versioning, chưa triển khai. |
| 9. Có cần expose mọi database table thành API không? | Không. Chỉ expose use case client cần và trường được phép; không tạo API công khai cho bảng token hay mọi cột User chỉ vì DB có bảng đó. | [`Route::get('orders', ...)`](../Modules/Shop/routes/api.php) | Expose use case xem đơn; không tự động mở mọi bảng DB. |
| 10. API design bắt đầu từ database hay use case? | Bắt đầu từ use case/nhu cầu consumer, rồi thiết kế quyền và contract; database là cách lưu trữ hỗ trợ nhu cầu đó. Có table không có nghĩa bắt buộc phải có endpoint tương ứng. | [`where('user_id', $request->user()->id)`](../Modules/Shop/app/Http/Controllers/Api/OrderController.php) | Thiết kế API theo nhu cầu user xem đơn của mình. |
