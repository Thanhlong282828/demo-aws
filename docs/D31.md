## Câu hỏi kiến thức và đáp án tham khảo

Cách học: tự trả lời trước, sau đó đối chiếu đáp án và source. Đáp án để ôn tập, không chứng nhận bạn đã tự làm hoặc đã đạt điểm.

**Câu 1. API documentation phục vụ ai?**

**Đáp án:** Cho developer/client tích hợp API, QA kiểm thử và người review project. Họ cần biết URL, method, headers, input, permission, response và status mà không phải đoán từ code.

**Câu 2. Postman dùng để làm gì?**

**Đáp án:** Dùng để gửi HTTP request, xem response và lưu các request/test scripts phục vụ kiểm tra API. Trong project, login script lưu token để thử request bảo vệ.

**Câu 3. Collection là gì?**

**Đáp án:** Là nhóm request có thể lưu, chia folder và chia sẻ cùng cấu hình/test scripts. Mini Shop Collection có Authentication, Products, Categories và Orders, tổng17 requests.

**Câu 4. Environment variable giúp gì?**

**Đáp án:** Cho phép đổi base_url, token hoặc id mà không sửa từng request. Chọn local hoặc production environment; base_url trong collection không có /api vì path request đã thêm /api.

**Câu 5. Vì sao không hard-code production token?**

**Đáp án:** Token hard-code dễ bị lộ khi chia sẻ/commit và nhanh hết hiệu lực. Export environment để token rỗng, login lại lấy token mới; đừng nhầm mật khẩu demo công khai với token hoạt động.

**Câu 6. Consistent JSON response quan trọng thế nào?**

**Đáp án:** Client có thể đọc data, message, errors theo quy ước chung thay vì viết logic riêng cho từng endpoint. List trong project thêm links/meta, detail có data object, validation có message/errors.

**Câu 7. Endpoint naming nên dùng noun hay action tùy tiện?**

**Đáp án:** Ưu tiên danh từ tài nguyên và HTTP method, như /products với GET/POST; tránh /getAllProducts, /deleteProduct tùy tiện. Một số thao tác đặc biệt như /login hoặc /logout được đặt tên theo use case rõ ràng.

**Câu 8. API versioning là gì ở mức concept?**

**Đáp án:** Là quản lý các phiên bản contract để thay đổi không tương thích không làm hỏng client cũ, ví dụ /api/v1 và /api/v2. Project hiện giữ /api/... theo đề, chưa triển khai version prefix.

**Câu 9. Có cần expose mọi database table thành API không?**

**Đáp án:** Không. Chỉ expose use case client cần và trường được phép; không tạo API công khai cho bảng token hay mọi cột User chỉ vì DB có bảng đó.

**Câu 10. API design bắt đầu từ database hay use case?**

**Đáp án:** Bắt đầu từ use case/nhu cầu consumer, rồi thiết kế quyền và contract; database là cách lưu trữ hỗ trợ nhu cầu đó. Có table không có nghĩa bắt buộc phải có endpoint tương ứng.
