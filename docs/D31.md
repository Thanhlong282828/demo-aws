## Câu hỏi kiến thức và đáp án tham khảo

Cách học: tự trả lời trước, sau đó đối chiếu đáp án và source. Đáp án để ôn tập, không chứng nhận bạn đã tự làm hoặc đã đạt điểm.

| Câu hỏi | Trả lời | Code nào → làm gì? |
| --- | --- | --- |
| 1.<br>API documentation phục vụ ai? | Cho developer/client tích hợp API, QA kiểm thử và người<br>review project.<br>Họ cần biết URL, method, headers, input, permission,<br>response và status mà không phải đoán từ code. | [`HTTP method / URL / body / response`](../docs/api.md)<br>→ Mô tả contract cho người gọi API. |
| 2.<br>Postman dùng để làm gì? | Dùng để gửi HTTP request, xem response và lưu các<br>request/test scripts phục vụ kiểm tra API.<br>Trong project, login script lưu token để thử request bảo vệ. | [`request`](../docs/postman/Mini-Shop-API.postman_collection.json)<br>→ Lưu request mẫu để gửi và kiểm tra response. |
| 3.<br>Collection là gì? | Là nhóm request có thể lưu, chia folder và chia sẻ cùng cấu<br>hình/test scripts.<br>Mini Shop Collection có Authentication, Products, Categories<br>và Orders, tổng17 requests. | [`item`](../docs/postman/Mini-Shop-API.postman_collection.json)<br>→ Gom request theo nhóm trong một collection. |
| 4.<br>Environment variable giúp gì? | Cho phép đổi base_url, token hoặc id mà không sửa từng<br>request.<br>Chọn local hoặc production environment<br>base_url trong collection không có /api vì path request đã<br>thêm /api. | [`base_url / token`](../docs/postman/local.postman_environment.json)<br>→ Đổi môi trường mà không sửa từng request. |
| 5.<br>Vì sao không hard-code production<br>token? | Token hard-code dễ bị lộ khi chia sẻ/commit và nhanh hết<br>hiệu lực.<br>Export environment để token rỗng, login lại lấy token mới<br>đừng nhầm mật khẩu demo công khai với token hoạt động. | [`{{token}}`](../docs/postman/Mini-Shop-API.postman_collection.json)<br>→ Tham chiếu token môi trường thay vì chép token<br>thật vào request. |
| 6.<br>Consistent JSON response quan trọng<br>thế nào? | Client có thể đọc data, message, errors theo quy ước chung<br>thay vì viết logic riêng cho từng endpoint.<br>List trong project thêm links/meta, detail có data object,<br>validation có message/errors. | [`toArray()`](../app/Http/Resources/ProductResource.php)<br>→ Giữ các trường sản phẩm nhất quán giữa các<br>response. |
| 7.<br>Endpoint naming nên dùng noun hay<br>action tùy tiện? | Ưu tiên danh từ tài nguyên và HTTP method, như /products với<br>GET/POST<br>tránh /getAllProducts, /deleteProduct tùy tiện.<br>Một số thao tác đặc biệt như /login hoặc /logout được đặt<br>tên theo use case rõ ràng. | [`Route::apiResource('products', ProductController::class)`](../Modules/Product/routes/api.php)<br>→ Dùng danh từ products và HTTP method cho CRUD. |
| 8.<br>API versioning là gì ở mức concept? | Là quản lý các phiên bản contract để thay đổi không tương<br>thích không làm hỏng client cũ, ví dụ /api/v1 và /api/v2.<br>Project hiện giữ /api/... theo đề, chưa triển khai version<br>prefix. | [`Route::apiResource('products', ProductController::class)`](../Modules/Product/routes/api.php)<br>→ Hiện dùng /api/products<br>/api/v1 là ý tưởng versioning, chưa triển khai. |
| 9.<br>Có cần expose mọi database table thành<br>API không? | Không.<br>Chỉ expose use case client cần và trường được phép<br>không tạo API công khai cho bảng token hay mọi cột User chỉ<br>vì DB có bảng đó. | [`Route::get('orders', ...)`](../Modules/Shop/routes/api.php)<br>→ Expose use case xem đơn<br>không tự động mở mọi bảng DB. |
| 10.<br>API design bắt đầu từ database hay use<br>case? | Bắt đầu từ use case/nhu cầu consumer, rồi thiết kế quyền và<br>contract<br>database là cách lưu trữ hỗ trợ nhu cầu đó.<br>Có table không có nghĩa bắt buộc phải có endpoint tương ứng. | [`where('user_id', $request->user()->id)`](../Modules/Shop/app/Http/Controllers/Api/OrderController.php)<br>→ Thiết kế API theo nhu cầu user xem đơn của mình. |
